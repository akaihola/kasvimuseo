# The complete runtime lock for the Python 2.7 stage, maintained by hand. Every
# package the application needs in order to run is named here at an exact
# version, so `pip install -r` this file installs that set and nothing else --
# with or without `--no-deps`, which was measured rather than assumed. It used
# to be half a picture: direct pins here, Pillow in `dev/Containerfile`, and
# nothing anywhere saying the two together were the dependency set. That was
# issue 027.
#
# By hand, because `uv pip compile` -- the mechanism `docs/upgrade-plan.rst`
# Appendix A uses for the locks from Stage 10 onwards -- cannot target this
# interpreter: `uv pip compile --python-version 2.7` answers "Invalid version
# request: Python <3.6 is not supported but 2.7 was requested". Asked for 3.7
# instead it reproduces exactly the set below except for the Pillow version,
# where it picks 9.5.0 -- correct for Stage 10, uninstallable here. So there is
# no generated `.in`/`.txt` pair before Stage 10, and this file is the lock.
#
# The upper bounds these packages need are in nobody's metadata -- the old ones
# declare lower bounds and nothing else -- so the ones that are known are
# written beside the pin that implies them, with the issue that establishes
# them. `setup.py` reads this file line by line into `install_requires`;
# setuptools drops the comment lines, so what it declares is exactly the pins
# below -- eight since upgrade plan Stage 6.
#
# Every one of them is a name and a version, resolvable from a package index
# and nothing else. That is issue 031: `django-jqm` used to be here as a URL
# pointing at a zip in a personal GitHub repository, so a build needed that URL
# to answer, and there was no version history behind it to reason about. It is
# vendored into `jqm/` in this repository now -- see `jqm/README.rst` -- and a
# build reaches nothing but PyPI.
# 1.9.13 is the last release in the 1.9 series (upgrade plan Stage 7). 1.9
# deletes `django.contrib.admin.util`, `EMPTY_CHANGELIST_VALUE` and the `url`
# tag of the `future` template library. The first two had one reader,
# `kasvimuseo/templatetags/kasvimuseo_admin_list.py`, which Stage 5 deleted;
# the third had one, `kasvimuseo/templates/admin/change_list.html`, and Stage 7
# deleted the `{% load url from future %}` line. 1.9 also starts warning about
# a `ForeignKey` with no `on_delete`, which 2.0 makes an error, so all 13 of
# them in `kasvimuseo/models.py` name `on_delete=models.CASCADE` since the same
# stage. The 1.8 pin before this one was an LTS and brought the one `TEMPLATES`
# setting; the Stage 6 section of `docs/upgrade-plan.rst` records that.
django==1.9.13
# Grappelli ships exactly one series per Django release and says so in its own
# README -- 2.5.x for Django 1.6, 2.6.x for 1.7, 2.7.x for 1.8, 2.8.x for 1.9
# -- so this pin is not a preference and cannot be skipped or deferred a stage;
# it moves whenever the line above does (issue 035). 2.8.3 is the last 2.8
# release on PyPI.
django-grappelli==2.8.3
# Issue 029: gunicorn <= 20.1.0 imports `pkg_resources`, and setuptools
# stopped shipping it in 82.0.0 -- resolving the middle upgrade stages without
# constraints picks exactly that pair, a gunicorn that cannot import. This pin
# is unaffected: 0.17.4 runs on Python 2.7, where setuptools 82 does not exist.
# The remedy is a plan decision rather than a bound here -- go straight to
# gunicorn 21.2.0 at the Python 3 flip (upgrade plan Stage 10), skipping 19.x
# and 20.x, so no `setuptools<82` has to be carried through eight stages.
gunicorn==0.17.4
psycopg2-binary==2.8.4
# Upgrade plan Stage 7: 3.4.1 -> 3.5.1. Stage 6's 3.4.1 was the first release
# to state Django 1.9 support, so the framework line above did not force this
# move; the plan's Stage 7 list asks for "3.5.1 or 3.6" and 3.5.1 is the
# nearer rung. Stage 8 takes 3.6, which is the release that added Django 1.10.
# Read 3.5.1 rather than 3.5: photologue's own CHANGELOG says 3.5 "failed to
# install under Python 2.7", because distutils choked on a non-ASCII filename
# (their issue #149), and 3.5.1 is the fix. This interpreter is Python 2.7, so
# 3.5 is not a candidate here at all.
#
# What 3.5.1 changes for this file: nothing in the pins, and two migrations in
# the database. `photologue/0009_auto_20160102_0904` rewrites
# `photo.date_taken`'s help text, and `0010_auto_20160105_1307` widens
# `title` and `slug` on both `photologue_photo` and `photologue_gallery` from
# `varchar(50)` to `varchar(250)`. That second one closes the oldest schema
# divergence this upgrade carries: the Stage 4 measurement found production's
# two `title` columns at `varchar(100)` where the model said 50, left there by
# Stage 2's faked South `0002`, and an `AlterField` re-types a column whatever
# its current width, so a restored database and a freshly-bootstrapped one both
# come out of this migration at 250.
django-photologue==3.5.1
# photologue's model dependency. Upgrade plan Stage 6 moved it 0.8.1 -> 1.1.1,
# because photologue 3.4.1 declares `django-sortedm2m>=1.1.1`. A pin below a
# declared floor is not a warning, it is a stopped application -- `manage` in
# the production image is a setuptools console script, and `pkg_resources`
# resolves the declared requirements of every installed distribution before
# it runs a line (`ContextualVersionConflict`: the half-day upgrade plan
# Stage 2 lost, and no stage since has repeated).
#
# 1.1.1 stays at Stage 7, and it is the Django 1.9 release of this package even
# though its classifiers stop at Django 1.8. The evidence is photologue's own
# CHANGELOG entry for 3.4.1, "Django 1.9 requires latest version of
# django-sortedm2m": photologue released 3.4.1 on 2015-12-23 and sortedm2m
# 1.1.1 on 2015-12-07, so 1.1.1 is the release that sentence points at, and
# `>=1.1.1` is the floor photologue wrote because of Django 1.9. Part 2.6 of
# `docs/upgrade-plan.rst` used to schedule 1.3.3 here; the Stage 7 section
# records why it does not, and the next real floor is photologue 3.7's
# `>=1.3.3` at Stage 9, where the pin moves with the package that asks for it.
#
# The build-tool constraint is issue 030, and it is about the *builder* rather
# than the version: every sortedm2m before 2.0.0 is sdist-only and its
# `setup.py` fails under setuptools >= 82, so this pin can only be built in a
# period-appropriate image. The Python 2.7 one here has setuptools 44.1.0, and
# Stage 10's `python:3.7-alpine` has 57.5.0.
django-sortedm2m==1.1.1
# photologue's as well, since it reads EXIF through this package from 3.4 on.
# 2.1.2 is the floor photologue declares, and also the ceiling this
# interpreter allows: it is the last release that ships a Python 2 wheel --
# from 2.2.0 on the wheels are tagged `py3` -- so this pin moves at the
# Python 3 flip (upgrade plan Stage 10) and not before.
ExifRead==2.1.2
# photologue's, not the application's: it declares `Pillow>=2.7.0` and nothing
# above, which is issue 027 in one line -- a resolver free to read that picks
# Pillow 12. Issue 028 is what that costs: photologue up to and including
# 3.15.1 calls `Image.ANTIALIAS`, removed in Pillow 10.0.0, from the branch
# that runs only when a cached photo size is missing, so it is a 500 on page
# render rather than an error at startup, and invisible to anyone with a warm
# cache. This pin therefore means `Pillow<10` as much as it means "the last
# release for Python 2.7". Move to 9.5.0 at the Python 3 flip (upgrade plan
# Stage 10): it is the last release that still has `ANTIALIAS`, and it is above
# the `Pillow>=9.1` that photologue 3.16 onwards needs for
# `Image.Resampling.LANCZOS` -- not the `Pillow>=9` its own metadata declares.
Pillow==6.2.2
# Not here either, and this is where they went: `django-extensions` and `six`.
# Upgrade plan Stage 0 moved `django-extensions` to `requirements/dev.txt`
# alone -- it is `runserver_plus` and `shell_plus`, nothing in this repository
# imports it, and `ylaneenkasvit/local_settings.development.py` is now what
# puts it into INSTALLED_APPS, so a production install has neither the package
# nor the app entry.
#
# `six` followed it, which the plan did not foresee: it lists `six` as Stage 10
# work, "Python 3 only", and Part 1 notes that nothing in this repository
# imports it. Neither says why it was installed at all. Measured in the image
# rather than reasoned: `django_extensions` is the only installed distribution
# that declares `six>=1.2`, and the only one with a file importing it -- 22 of
# them. Django 1.5 vendors its own copy as `django.utils.six`; `django`,
# `django-photologue`, `django-grappelli`, `south`, `gunicorn`,
# `psycopg2-binary` and `Pillow` neither declare it nor import it. So with
# django-extensions out of production, `six` is a runtime dependency of nothing
# here, and a complete runtime lock cannot keep naming it. It is pinned in
# `dev.txt` instead, where the package that needs it is. The test stack pulls
# its own (`pytest`, `mock`), which is why the suite is unaffected.
#
# `django-sortedm2m` used to be named here only to say it was absent:
# `dev/Containerfile` installed it beside Pillow and called both photologue's
# runtime dependencies, and photologue 2.6.1's were `Django>=1.4`,
# `South>=0.7.5` and `Pillow>=2.0.0` alone. Stage 2 is where it becomes real,
# so it is pinned above with the rest of the runtime -- and its metadata
# declares it, which the plan predicted would not happen until photologue 3.4.
