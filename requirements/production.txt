# The complete runtime lock for the Python 2.7 stage, maintained by hand. Every
# package the application needs in order to run is named here at an exact
# version, so `pip install -r` this file installs that set and nothing else --
# with or without `--no-deps`, which was measured rather than assumed. It used
# to be half a picture: direct pins here, Pillow in `dev/Containerfile`, and
# nothing anywhere saying the two together were the dependency set. That was
# issue 027.
#
# By hand, because `uv pip compile` -- the mechanism `docs/upgrade-plan.rst`
# Appendix A uses for the locks from Stage 10 onwards -- cannot target this
# interpreter: `uv pip compile --python-version 2.7` answers "Invalid version
# request: Python <3.6 is not supported but 2.7 was requested". Asked for 3.7
# instead it reproduces exactly the set below except for the Pillow version,
# where it picks 9.5.0 -- correct for Stage 10, uninstallable here. So there is
# no generated `.in`/`.txt` pair before Stage 10, and this file is the lock.
#
# The upper bounds these packages need are in nobody's metadata -- the old ones
# declare lower bounds and nothing else -- so the ones that are known are
# written beside the pin that implies them, with the issue that establishes
# them. `setup.py` reads this file line by line into `install_requires`;
# setuptools drops the comment lines, so what it declares is the nine pins
# below -- eleven since upgrade plan Stage 2 added photologue 2.8's own two
# dependencies.
#
# Every one of them is a name and a version, resolvable from a package index
# and nothing else. That is issue 031: `django-jqm` used to be here as a URL
# pointing at a zip in a personal GitHub repository, so a build needed that URL
# to answer, and there was no version history behind it to reason about. It is
# vendored into `jqm/` in this repository now -- see `jqm/README.rst` -- and a
# build reaches nothing but PyPI.
# 1.6.11 is the last release in the 1.6 series (upgrade plan Stage 3). What it
# costs this project is one import -- `django.conf.urls.defaults` is gone, and
# both `urls.py` files import from `django.conf.urls` now -- and three pins
# that have to move with it, below. Django's own packaging accident stopped at
# 1.5.12 and stays stopped: 1.6.11 collects the locale catalogs, fixtures and
# `project_template` as `package_data`, so they land inside the package
# whichever way pip installs it (issue 040). Both image definitions keep the
# assertion that they are readable there -- see the comment beside it in
# `dev/Containerfile`.
#
# The next stage that touches this line is Stage 5, and it is the expensive
# one: 1.7 takes South away.
django==1.6.11
# Grappelli ships exactly one series per Django release and says so in its own
# README -- 2.4.x for Django 1.4/1.5, 2.5.x for 1.6, 2.6.x for 1.7 -- so this
# pin is not a preference and cannot be skipped or deferred a stage; it moves
# whenever the line above does (issue 035). 2.5.7 is the last 2.5 release on
# PyPI, and it is the one this project ran the admin on.
django-grappelli==2.5.7
# Issue 029: gunicorn <= 20.1.0 imports `pkg_resources`, and setuptools
# stopped shipping it in 82.0.0 -- resolving the middle upgrade stages without
# constraints picks exactly that pair, a gunicorn that cannot import. This pin
# is unaffected: 0.17.4 runs on Python 2.7, where setuptools 82 does not exist.
# The remedy is a plan decision rather than a bound here -- go straight to
# gunicorn 21.2.0 at the Python 3 flip (upgrade plan Stage 10), skipping 19.x
# and 20.x, so no `setuptools<82` has to be carried through eight stages.
gunicorn==0.17.4
psycopg2-binary==2.8.4
# 1.0.2 is South's last release. It supports Django 1.6 and never 1.7, which is
# the whole shape of upgrade plan Stage 5: the framework cannot move again until
# this package is gone. Nothing declares an upper bound on it because there is
# no release above it to bound.
#
# 0.8.1, which this was, predates 1.6 and branches on it in two places that
# matter here -- both added in 1.0 and neither reachable by a version test in
# this repository:
#
# * `LoadInitialDataMigrator` is what loads `kasvimuseo/fixtures/
#   initial_data.json` after `migrate` rather than during `syncdb` (issue 055).
#   0.8.1 does it by swapping `django.db.models.get_apps` out from under
#   `loaddata`; 1.0.2 has a separate `post_1_6` path that builds a fresh
#   `AppCache` instead, because 1.6's `loaddata` no longer reads the module
#   attribute the old trick replaced.
# * `south.hacks.django_1_0.Hacks.repopulate_app_cache` writes
#   `cache.handled = set()` on 1.6 and `{}` below it -- 1.6 changed that
#   attribute's type, and South goes through this every time it puts
#   INSTALLED_APPS back, which `syncdb` and every test-database build do.
south==1.0.2
# Upgrade plan Stage 2: 2.6.1 -> 2.8.3, moved alone and ahead of the framework
# because photologue owns database tables. 2.7 prefixed every setting name with
# `PHOTOLOGUE_` (this project sets none of them, so that half is a no-op) and
# 2.8 renamed `title_slug` to `slug` on `Photo` and `Gallery`, gave both a
# `sites` M2M -- which is why `django.contrib.sites` and `SITE_ID` are in
# `common_settings.py` now -- and grew the two dependencies below. Its own
# South migrations run this project's photologue tables forward:
# `SOUTH_MIGRATION_MODULES` and the local squashed copy of its `0001_initial`
# are gone with this pin.
django-photologue==2.8.3
# photologue 2.8's two new dependencies, both of which need an upper bound --
# one of them declared and one of them nobody's, which is issue 027 twice over.
# photologue 2.8.3's `requirements.txt`, which its `setup.py` reads into
# `install_requires`, asks for `django-sortedm2m>=0.6.1,<0.8` and
# `django-model-utils>=2.0.3`.
#
# `django-model-utils` has a hard ceiling: photologue imports
# `model_utils.managers.PassThroughManager`, and 2.4 deleted that class
# outright (it is in 2.0.3, 2.2 and 2.3.1 and in no release after them), so
# anything from 2.4 up is an ImportError at startup. 2.3.1 is therefore the
# last usable release rather than a preference, and it still branches on
# `django.VERSION < (1, 6)` internally. photologue drops the dependency
# entirely at 3.2 -- upgrade plan Stage 6 -- so this pin never has to move.
#
# `django-sortedm2m` is pinned *inside* photologue's declared range, and the
# upgrade plan asked for 1.1.1 or later. 1.5.0 was tried first, on the reading
# that the `<0.8` is stale metadata: the field API photologue uses does not
# change across the 1.x line, the suite passes on it and both images install
# it, because pip 20.0.2 resolves with the legacy resolver and only warns. What
# it breaks is the production image at *runtime*. `manage` there is a
# setuptools console script, and a console script resolves the declared
# requirements of every installed distribution through `pkg_resources` before
# it runs a line: with 1.5.0 installed, `manage validate` -- and `manage
# migrate`, which is how this stage is deployed -- dies with
# `ContextualVersionConflict: (django-sortedm2m 1.5.0, ...
# Requirement.parse('django-sortedm2m<0.8,>=0.6.1'), set(['django-photologue']))`.
# The development image never sees it, because there the same commands run as
# `python ylaneenkasvit/manage.py`. So the declared ceiling is load-bearing
# whether or not it is justified, and 0.7.0 is the newest release under it.
#
# It costs nothing here. photologue 2.8 uses `SortedManyToManyField` and the
# `sort_value` column, both of which 0.7.0 has, and it is one release older
# than the 1.1.1 the plan named. The next real floor is photologue 3.7, which
# declares `django-sortedm2m>=1.3.3` -- upgrade plan Stage 7, where the pin
# moves with the package that asks for it.
#
# The build-tool constraint is issue 030, and it is about the *builder* rather
# than the version: every sortedm2m before 2.0.0 is sdist-only and its
# `setup.py` fails under setuptools >= 82, so this pin can only be built in a
# period-appropriate image. The Python 2.7 one here has setuptools 44.1.0, and
# Stage 10's `python:3.7-alpine` has 57.5.0.
django-sortedm2m==0.7.0
django-model-utils==2.3.1
# photologue's, not the application's: it declares `Pillow>=2.0.0` and nothing
# above, which is issue 027 in one line -- a resolver free to read that picks
# Pillow 12. Issue 028 is what that costs: photologue up to and including
# 3.15.1 calls `Image.ANTIALIAS`, removed in Pillow 10.0.0, from the branch
# that runs only when a cached photo size is missing, so it is a 500 on page
# render rather than an error at startup, and invisible to anyone with a warm
# cache. This pin therefore means `Pillow<10` as much as it means "the last
# release for Python 2.7". Move to 9.5.0 at the Python 3 flip (upgrade plan
# Stage 10): it is the last release that still has `ANTIALIAS`, and it is above
# the `Pillow>=9.1` that photologue 3.16 onwards needs for
# `Image.Resampling.LANCZOS` -- not the `Pillow>=9` its own metadata declares.
Pillow==6.2.2
# Not here either, and this is where they went: `django-extensions` and `six`.
# Upgrade plan Stage 0 moved `django-extensions` to `requirements/dev.txt`
# alone -- it is `runserver_plus` and `shell_plus`, nothing in this repository
# imports it, and `ylaneenkasvit/local_settings.development.py` is now what
# puts it into INSTALLED_APPS, so a production install has neither the package
# nor the app entry.
#
# `six` followed it, which the plan did not foresee: it lists `six` as Stage 10
# work, "Python 3 only", and Part 1 notes that nothing in this repository
# imports it. Neither says why it was installed at all. Measured in the image
# rather than reasoned: `django_extensions` is the only installed distribution
# that declares `six>=1.2`, and the only one with a file importing it -- 22 of
# them. Django 1.5 vendors its own copy as `django.utils.six`; `django`,
# `django-photologue`, `django-grappelli`, `south`, `gunicorn`,
# `psycopg2-binary` and `Pillow` neither declare it nor import it. So with
# django-extensions out of production, `six` is a runtime dependency of nothing
# here, and a complete runtime lock cannot keep naming it. It is pinned in
# `dev.txt` instead, where the package that needs it is. The test stack pulls
# its own (`pytest`, `mock`), which is why the suite is unaffected.
#
# `django-sortedm2m` used to be named here only to say it was absent:
# `dev/Containerfile` installed it beside Pillow and called both photologue's
# runtime dependencies, and photologue 2.6.1's were `Django>=1.4`,
# `South>=0.7.5` and `Pillow>=2.0.0` alone. Stage 2 is where it becomes real,
# so it is pinned above with the rest of the runtime -- and its metadata
# declares it, which the plan predicted would not happen until photologue 3.4.
