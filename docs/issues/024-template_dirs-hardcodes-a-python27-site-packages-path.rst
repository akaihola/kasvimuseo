=================================================================
Issue 024: TEMPLATE_DIRS hardcodes a python2.7 site-packages path
=================================================================

:Status: Fixed
:Severity: Medium
:Area: settings / Python 3 migration
:Reported: 2026-07-28
:Source: Dependency upgrade analysis, branch ``requirements-update-plan``
:Evidence: ``kasvimuseo/tests/test_settings_template_dirs.py`` -- added with the fix; before it nothing asserted where photologue's templates came from
:Depends on: (none)
:Blocks: 036 -- blocks Stage 10, the Python 3 flip
:Related: 016 -- the other Python 3 landmine already on file
:Decision: Delete the second entry and rely on Django's app template loader, which is in the 1.5 default ``TEMPLATE_LOADERS`` this project does not override. The path resolved to nothing in the container already, so nothing that runs today changes.
:Resolution: 5677f78 -- the one-tuple in ``ylaneenkasvit/common_settings.py`` and the test

Problem
=======

``ylaneenkasvit/common_settings.py``::

    TEMPLATE_DIRS = (here('templates'),
                     here('..', 'lib', 'python2.7', 'site-packages',
                          'photologue', 'templates'))

The second entry reaches into the virtualenv's ``site-packages`` by literal
path to find photologue's templates. It encodes the interpreter version,
``2.7``, in a settings file.

This is also unnecessary. Django's app template loader finds templates inside
installed applications automatically; photologue is already in
``INSTALLED_APPS``.

Impact
======

A hard blocker for the Python 3 migration: on Python 3.7 the directory is
``lib/python3.7/site-packages`` and the entry silently resolves to nothing.
Silently, because a missing template directory is not an error -- templates
would simply stop being found, and the photologue admin pages would break with
``TemplateDoesNotExist`` rather than anything pointing at this line.

It also breaks under any layout that is not a virtualenv with the project
installed beside it, which includes the current container.

Options
=======

Delete the second entry and rely on the app template loader. Verify by checking
that the photologue admin pages still render.

This is folded into Stage 6 of ``docs/upgrade-plan.rst``, where
``TEMPLATE_DIRS`` is replaced by ``TEMPLATES`` with ``APP_DIRS = True``
anyway -- but it can be done on its own at any time, and doing it early
removes one item from the Python 3 flip.

Decision
========

Done as described above: ``TEMPLATE_DIRS`` is now the one-tuple
``(here('templates'),)``. The ``TEMPLATES``/``APP_DIRS`` conversion is *not*
done here -- Django 1.5 has no ``TEMPLATES`` setting and would ignore it, which
is this issue's own failure mode -- so Stage 6 still owns it and has one item
less to do.

**The path did not resolve, and had not for as long as the container has
existed.** ``here`` is relative to ``ylaneenkasvit/``, so the entry expanded to
``/src/ylaneenkasvit/../lib/python2.7/site-packages/photologue/templates`` in
the development container, and ``/src`` -- the bind-mounted working copy -- has
no ``lib/`` at all: ``dev/Containerfile`` installs the dependencies into the
image, at ``/usr/local/lib/python2.7/site-packages``. ``os.path.isdir`` on the
expanded path answers ``False``. So this was not a working configuration being
replaced by another one; it was a line Django has been silently ignoring, and
photologue's templates were already being found by the app loader.

That loader is active by default rather than by configuration. Neither
``common_settings.py`` nor any of the settings modules that import from it
names ``TEMPLATE_LOADERS``, and ``django.conf.global_settings`` in the
container -- Django 1.5.1, the pin in ``requirements/production.txt``, read
there rather than from memory -- has::

    TEMPLATE_LOADERS = ('django.template.loaders.filesystem.Loader',
                        'django.template.loaders.app_directories.Loader')

``photologue`` is in ``INSTALLED_APPS`` and ships its templates inside the
package, at ``photologue/templates/photologue/``, so
``app_directories.Loader`` finds them.

One thing the original report gets slightly wrong is worth recording, since it
is what "verify the photologue admin pages" would have tested: **photologue
ships no admin templates.** The fourteen files under its ``templates/`` are the
public gallery and photo pages plus two inclusion tags; the admin pages are
rendered by Django's and grappelli's own templates and were never affected by
this entry either way. The pages this line could have broken are the public
ones, and those are what was checked.

Verification
============

The suite passes (389 tests), and the pages were loaded over HTTP from
``dev/kasvimuseo app run`` against a bootstrapped database seeded with one
gallery and one photo, rather than reasoned about. All answered ``200`` with
their content, and no ``TemplateDoesNotExist`` appeared in the server log:

* ``/photologue/gallery/`` -- the archive index, which issue 008 re-declared
  ahead of the include; lists "Kesa 2012"
* ``/photologue/gallery/kesa-2012/``, ``/photologue/gallery/2026/``,
  ``/photologue/gallery/2026/jul/``, ``/photologue/gallery/2026/jul/31/``
* ``/photologue/photo/``, ``/photologue/photo/kukka/``,
  ``/photologue/photo/2026/``, ``/photologue/photo/2026/jul/``,
  ``/photologue/photo/2026/jul/31/``

and, logged in as a superuser, the photologue admin pages the report names --
``/admin/photologue/photo/``, ``/admin/photologue/gallery/``,
``/admin/photologue/photosize/``, ``/admin/photologue/photo/add/`` and the two
change forms -- which render from Django's and grappelli's templates as above.

The regression test is ``kasvimuseo/tests/test_settings_template_dirs.py``: it
pins the one-tuple, that no template directory reaches into ``site-packages``,
that the app loader is in the default this project inherits, that
``photologue/gallery_archive.html`` is loaded from inside the installed
package, and that the gallery index renders through it.
